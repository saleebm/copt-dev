I’ve been thinking about the gap between what we are asked to build and what actually ships. I recently read a post by Thorsten Ball that perfectly captures why this happens. He simply copy-pasted an unedited Slack message he sent to his team at Amp, and reading it felt like looking in a mirror. Thorsten argues that "building new software is learning". We usually treat software engineering like a construction project where we just need a better blueprint. But when you are building something entirely new, you literally cannot know what you are making until you start making it. You are guaranteed to run into a "that’s not what I meant" moment from stakeholders or users. This guy gets it. The takeaway isn't to spend four weeks writing a tighter specification document. The goal, as Thorsten puts it, is "reducing the time it takes you to go from 'let me try something' to getting your ass whooped by reality". I’ve seen this play out on my own teams. The developers who ship the best work are the ones who fake a demo video, write the README API before writing a single function, or cobble together a one-hour prototype just to get told they are wrong faster. They treat the code as a disposable tool for extracting feedback. If we want to build better software, we have to stop trying to be right on the first try and start optimizing for how quickly we can afford to be wrong.
